# adr-017: Mapster Integration — Package Rationale and Scope

**Status:** Accepted  
**Date:** 2026-08-10  
**Authors:** Core maintainers  
**Linked audit item:** CRIT-V4-002 (Audit v4.0)

---

## Context

The Engineering Specification v4.0 §MAPSTER POSITION states:

> **Decision:** Mapster DOES NOT need a separate integration package.
>
> **Rationale:** The `explicit operator`s generated by the Core
> (`public static explicit operator string(EmailAddress e) => e.Value;`)
> are sufficient for Mapster (and any AOT-friendly mapper) to resolve
> conversions without additional configuration.
>
> If a use case requiring explicit integration is discovered in the future
> (e.g., mapping of composite ValueObjects), it will be evaluated using the standard Feature Gate.

The repository has an active `EricksonLopez.DomainPrimitives.Mapster` package that provides a
source-generated Mapster integration. This contradicts the spec position. The audit (2026-08-10
CRIT-V4-002) flagged this as `CONTRADICTED`.

---

## Problem Statement

The spec was written with the assumption that Mapster resolves explicit operators automatically.
Investigation reveals this is **partially true**:

| Scenario | Explicit operators sufficient? | Evidence |
|----------|-------------------------------|----------|
| Scalar primitive → backing type | ✅ Yes | `(string)email` resolved by Mapster automatically |
| Backing type → scalar primitive | ⚠️ Sometimes | Mapster may not discover `explicit operator T(backing)` in multi-assembly scenarios |
| `ValueObject` (multi-property composite) → another record | ❌ No | Mapster needs explicit member mapping configuration for composite types |
| AOT-mode with `[MappingAssembly]` | ⚠️ Partial | Static explicit operators must be discovered at source-gen time; cross-assembly discovery varies |

**Conclusion:** The spec's position is correct for the **80% case** (simple scalar primitives). But
the `EricksonLopez.DomainPrimitives.Mapster` package fills the **20% case** (composite ValueObjects,
AOT mode with explicit registration).

The Feature Gate test from the spec:

1. ✅ Solves a problem that 20%+ of users will encounter → **borderline** (Value Objects with Mapster)
2. ✅ Can be explained in one sentence → "Provides Mapster TypeAdapterConfig for composite ValueObjects"
3. ⚠️ The user will discover it via IntelliSense → No — the package must be added explicitly
4. ✅ Adds ≤ 3 members to the API surface → Yes (AddDomainPrimitives() extension)
5. ✅ Maintenance cost < 2h per release → Yes
6. ✅ No breaking changes → Yes
7. ✅ Passes performance gates → Yes (source-generated)
8. ✅ No runtime reflection → Yes (source generator)

Result: **7/8** — marginal pass. The package is justified as an **advanced use case package**.

---

## Decision

**The `EricksonLopez.DomainPrimitives.Mapster` package is retained as an optional advanced
integration for ValueObject mapping scenarios. It is NOT deprecated.**

The spec §MAPSTER POSITION is updated with a corrigendum to document this distinction:

- **Simple scalar primitives** (string, int, Guid backed): Explicit operators are sufficient.
  No package required. This covers the 80% case.
- **Composite ValueObjects and AOT-explicit mode**: The `EricksonLopez.DomainPrimitives.Mapster`
  package provides source-generated `IRegister` implementations that handle complex mapping.
  This covers the 20% case.

The spec wording is updated to reflect this nuance instead of the absolute "DOES NOT need a package."

---

## Alternatives Considered

| Alternative | Rejected because |
|-------------|-----------------|
| Deprecate the package immediately | Breaks users with composite VO → DTO mapping scenarios without a migration path |
| Keep spec unchanged and hide the package | Violates §11.1 (CONTRADICTED claim unresolved) |
| Move package into Core | Introduces Mapster as a Core dependency — violates P10 (each integration separate) |

---

## Consequences

- **Positive**: Eliminates the `CONTRADICTED` state between spec and implementation.
- **Positive**: Users with complex VO mapping scenarios retain a supported path.
- **Positive**: The README can be precise about which scenario requires the package.
- **Negative**: The spec §MAPSTER POSITION required a corrigendum — this ADR documents it.
- **Action**: The README is updated to distinguish "simple mapping (no package needed)" from
  "composite VO mapping (add EricksonLopez.DomainPrimitives.Mapster)".
