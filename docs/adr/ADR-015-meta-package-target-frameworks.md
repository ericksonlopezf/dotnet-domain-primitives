# ADR-015: Meta-Package Target Framework Strategy

**Status:** Accepted  
**Date:** 2026-08-10  
**Authors:** Core maintainers  
**Linked audit item:** MED-006

---

## Context

The `EricksonLopez.DomainPrimitives` solution is split into multiple packages:

| Package | TFMs | Purpose |
|---------|------|---------|
| `EricksonLopez.DomainPrimitives.Abstractions` | `netstandard2.0;net8.0;net9.0;net10.0` | Attributes, marker interfaces, `PrimitiveError` |
| `EricksonLopez.DomainPrimitives.Generators` | `netstandard2.0` | Roslyn source generator (analyzer assembly) |
| `EricksonLopez.DomainPrimitives.Analyzers` | `netstandard2.0` | Roslyn diagnostic analyzers |
| **`EricksonLopez.DomainPrimitives`** | **`net8.0;net9.0;net10.0`** | Meta-package (runtime) |

The question: **Why does the meta-package not include `netstandard2.0`?**

---

## Decision

The `EricksonLopez.DomainPrimitives` meta-package deliberately targets only `net8.0;net9.0;net10.0` and will **not** include `netstandard2.0`.

---

## Rationale

### 1. Runtime API dependencies on modern BCL

The Core runtime package depends on APIs that are unavailable or degraded in `netstandard2.0`:

| API | Minimum TFM | Reason |
|-----|------------|--------|
| `System.Diagnostics.Metrics.Meter` | NET6+ | OpenTelemetry metrics |
| `System.Text.Json.Utf8JsonReader.ValueSpan` | NET5+ | Zero-allocation JSON deserialization (CRIT-002) |
| `ISpanFormattable` | NET6+ | Required by `ISpanFormattable` interface implementation |
| `ISpanParsable<T>` | NET7+ | Required by `IParsable<T>` + `ISpanParsable<T>` |
| `IUtf8SpanParsable<T>` | NET8+ | Zero-allocation UTF-8 parse path |
| `System.Numerics.IEqualityOperators<T,U,TResult>` | NET7+ | Generated by `ValueObjectGenerator` (CRIT-004) |
| `RegexOptions.NonBacktracking` | NET7+ | SEC-002 security gate |
| `System.Buffers.ArrayPool<T>` (span overload) | NET5+ | SEC-006 ArrayPool path |

Supporting `netstandard2.0` in the runtime package would require either:
- Polyfilling all of the above APIs (significant maintenance burden)
- Conditionally removing features per TFM (violates the library's zero-compromise design principle)

### 2. The correct migration path for netstandard2.0 consumers

Consumers targeting `netstandard2.0` (e.g., old .NET Framework 4.8 or older Xamarin targets) should reference only:
```xml
<!-- Provides: attributes, marker interfaces, PrimitiveError -->
<PackageReference Include="EricksonLopez.DomainPrimitives.Abstractions" Version="1.x.x" />
```

The source generator and analyzer are automatically included as analyzer references (no runtime dependency):
```xml
<!-- Source generator — no runtime dep, automatically runs during build -->
<PackageReference Include="EricksonLopez.DomainPrimitives.Generators" Version="1.x.x">
  <PrivateAssets>all</PrivateAssets>
  <IncludeAssets>runtime; build; native; contentfiles; analyzers</IncludeAssets>
</PackageReference>
```

The generated code for `netstandard2.0` uses a reduced feature set (no `ISpanFormattable`, no `NonBacktracking` regex) gated with `#if NET7_0_OR_GREATER` and `#if NET8_0_OR_GREATER`.

### 3. Forward compatibility horizon

The 15-year design horizon (2026–2041) targets active .NET LTS versions. `netstandard2.0` consumer scenarios are strictly legacy/interop. Adding it to the meta-package would create permanent maintenance drag for a declining audience.

---

## Alternatives Considered

| Alternative | Rejected because |
|-------------|-----------------|
| Multi-target meta-package with `#if` everywhere | 47+ conditional compilation blocks; prohibitive maintenance cost |
| Separate `EricksonLopez.DomainPrimitives.Legacy` package | Fragmentation; confusion about which package to use |
| Polyfill packages (e.g., `PolySharp`) | Adds a transitive runtime dependency; contradicts zero-dependency policy |

---

## Consequences

- **Positive**: No degraded feature paths in the runtime assembly. All users on supported TFMs get the full feature set.
- **Positive**: The spec's zero-allocation, NativeAOT-ready, SEC-compliant design is fully achievable.
- **Negative**: Consumers on `netstandard2.0` cannot use the meta-package directly. They must reference `Abstractions` separately. This is documented in the README.
- **Negative**: The meta-package cannot be used in full .NET Framework 4.x projects (by design — NET Framework is out of scope per the spec's 15-year horizon).
