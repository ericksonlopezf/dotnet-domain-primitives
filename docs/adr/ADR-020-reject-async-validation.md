# ADR-020: Reject Async Validation and Async Factories

**Date:** 2026-08-10
**Status:** Accepted
**Authors:** Core maintainers
**Related audit items:** REJECT-002 (feature-gaps.md)

---

## Context

Some user requests and community discussions propose adding async variants of factory methods:

```csharp
// Proposed (rejected) pattern:
var email = await EmailAddress.CreateAsync("user@example.com");
var (success, result, error) = await EmailAddress.TryCreateAsync("user@example.com");
```

The motivation is typically to support validation that requires I/O (e.g., checking email
uniqueness in a database, verifying a domain exists via DNS lookup).

---

## Decision

**`EricksonLopez.DomainPrimitives` will never generate async factory methods or support
async validation hooks.**

---

## Rationale

### 1. Domain validation must be intrinsic

A core principle of Domain-Driven Design is that a Value Object's validity is determined solely
by its internal state — never by an external system. Validation that requires I/O (database
lookup, HTTP call, DNS query) is by definition **application-level** or **infrastructure-level**
validation, not **domain-level** validation.

```
Domain Primitive Contract:
  "Is this string a syntactically valid email address?"  ← Domain validation ✅
  "Does this email address belong to an existing user?"  ← Application validation ❌
```

If a primitive requires async validation, the design is wrong — the check belongs in the
Application Layer (Command Handler, Domain Service, Repository), not in the Value Object
constructor.

### 2. Async constructors violate the zero-allocation hot path

`Task<T>` and `ValueTask<T>` both allocate on the heap (even `ValueTask<T>` may allocate the
backing `IValueTaskSource<T>`). The allocation model of `TryCreate` is:

- **Synchronous success:** 0 allocations (struct result on stack, no Task wrapping).
- **Synchronous failure:** 1 allocation (error message string).

An async factory path eliminates this guarantee entirely.

### 3. `async` methods cannot be generated by Roslyn source generators in a useful way

A source generator cannot emit an `async` method that awaits an application-provided delegate
because the delegate's type is unknown at generation time. The generated async method would
require either:

- A `Func<T, CancellationToken, Task<bool>>` delegate parameter on the factory method, making
  the factory method dependent on application infrastructure — which violates the library's
  separation of concerns.
- Or a `partial` async method, which C# does not support in a meaningful way for return types
  other than `void`.

### 4. Thread-safety and reentrancy guarantees would be lost

Domain Primitive creation must be deterministic and thread-safe. If creation involves I/O,
the outcome can differ between invocations of the same input (e.g., network failure, race
condition on a database check). This makes the type non-deterministic and unsafe to use as a
dictionary key or in equality comparisons.

---

## Correct Pattern

Async validation belongs in the Application Layer:

```csharp
// ✅ Correct: Domain primitive validates format synchronously
if (!EmailAddress.TryCreate(rawEmail, out var email, out var error))
    return ValidationError(error);

// ✅ Correct: Application service performs async uniqueness check
if (await _userRepository.ExistsAsync(email, ct))
    return ConflictError("Email already registered");

// ✅ Correct: Primitive is created after all async checks pass
var user = User.Create(email, ...);
```

---

## Alternatives Considered

| Alternative | Rejected because |
|-------------|-----------------|
| `TryCreateAsync` with optional async validator delegate | Requires injecting infrastructure into the domain layer. The delegate must be provided by the caller, leaking application concerns into the domain. |
| `IAsyncValidator<T>` interface on the partial type | Requires the user to implement infrastructure interfaces on their domain type — contamination of the domain layer. |
| Partial `ValidateAsync` hook (similar to partial `Validate`) | C# 12 does not support `partial async` methods with non-void return types in a way that source generators can usefully emit. |

---

## Consequences

- **Positive:** Domain primitives remain pure — their validity depends only on their value.
- **Positive:** Zero-allocation guarantee is preserved.
- **Positive:** Thread safety is guaranteed.
- **Negative:** Users who conflate domain and application validation must refactor. The
  migration path is to move async checks to the Application Layer.
- **Documentation action:** Documented in `docs/REJECTED-FEATURES.md` with the correct
  pattern shown.
