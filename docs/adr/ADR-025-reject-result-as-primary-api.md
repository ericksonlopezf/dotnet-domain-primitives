# ADR-025: Reject Result<T> as Primary Error API Pattern

**Date:** 2026-08-10
**Status:** Accepted
**Authors:** Core maintainers
**Related audit items:** REJECT-006 (feature-gaps.md)
**Supersedes:** ADR-003 (TryCreate result pattern), aligns with ADR-006 (ValidationError over Result)

---

## Context

Several .NET functional programming libraries (CSharpFunctionalExtensions, LanguageExt,
FluentResults, ErrorOr) use a `Result<T, TError>` monad as the primary error-handling pattern.
Vogen generates `ValueObjectOrError<T>`. Thinktecture generates `Result<T, ValidationError>`.

Multiple community requests ask whether `EricksonLopez.DomainPrimitives` will support a
`Result<T>`-returning variant of `TryCreate` or offer Railway-Oriented Programming integration.

The current API:
- `Create(TValue)` — throws `DomainPrimitiveValidationException` on failure.
- `TryCreate(TValue, out TSelf result, out PrimitiveError error)` — returns `bool`.

---

## Decision

**`Result<T>` will not be the primary error API. The `out`-based `TryCreate` pattern is
the definitive API and will not be replaced.**

`Result<T>` support MAY be provided as a thin user-side adapter pattern (documented in the
cookbook) but will never be generated by the source generator.

---

## Rationale

### 1. `Result<T>` allocates on the heap

Any `Result<T, TError>` implementation that is a `class` or contains a `class` reference
(e.g., an error message string in the error case) allocates on the managed heap.

`EricksonLopez.DomainPrimitives` generates `PrimitiveError` as a `readonly struct` (value type).
The `TryCreate(out TSelf result, out PrimitiveError error)` pattern:

- On **success**: `result` is a `readonly record struct` on the caller's stack. `error` is
  `default(PrimitiveError)`. **Zero heap allocations**.
- On **failure**: `error` is a `PrimitiveError` struct on the caller's stack (no boxing).
  The error message string is the only allocation. **One allocation** (the message string).

A `Result<T>` wrapper would add at minimum one heap allocation on *every* call (the Result
object itself), degrading the success-path allocation model from 0 to 1.

### 2. `Result<T>` creates coupling to a specific Result library

There is no standard `Result<T>` type in the .NET BCL. Every `Result<T>`-based library defines
its own type. If the generator emits a `Result<T>`, it must depend on one of:

- `FluentResults.Result<T>`
- `ErrorOr.ErrorOr<T>`
- `CSharpFunctionalExtensions.Result<T>`
- `LanguageExt.Either<L, R>`
- A custom `EricksonLopez.DomainPrimitives.Result<T>`

Each choice forces that library on every consumer. A custom Result type creates yet another
fragmentation in an already fragmented ecosystem.

### 3. The `out`-pattern is the BCL standard

The .NET BCL uses the `TryXxx(out T result)` pattern consistently:

- `int.TryParse(string, out int result)`
- `DateTime.TryParse(string, out DateTime result)`
- `Uri.TryCreate(string, UriKind, out Uri result)`
- `Guid.TryParse(string, out Guid result)`

`TryCreate(TValue, out TSelf result, out PrimitiveError error)` is a direct extension of this
idiom, adding a typed error parameter. It is idiomatic C# with no learning curve for .NET
developers.

### 4. Railway-Oriented Programming is the Application Layer's responsibility

If a consumer wants to chain operations Railway-style, they can wrap `TryCreate`:

```csharp
// User-side adapter — zero library dependency required:
public static ErrorOr<EmailAddress> ToErrorOr(string raw)
{
    return EmailAddress.TryCreate(raw, out var email, out var error)
        ? email
        : Error.Validation(error.Code, error.Message);
}
```

This pattern requires no library support and produces the user's preferred `Result<T>` type.
Generating this in the source generator would require knowledge of the user's preferred Result
library — which is an application concern, not a library concern.

---

## Alternatives Considered

| Alternative | Rejected because |
|-------------|-----------------|
| Generate a library-agnostic `PrimitiveResult<T>` type | Adds another Result type to the ecosystem. Users still need adapters to convert to their preferred type. |
| Accept a `Func<TSelf, PrimitiveError, TResult>` delegate to `TryCreate` | Makes the API significantly more complex and breaks the zero-allocation guarantee (delegate allocation). |
| Provide `ToErrorOr()`, `ToResult()` extension methods via optional packages | Ties the library to specific Result libraries. Maintenance cost for every supported Result library. |

---

## Consequences

- **Positive:** Success-path zero-allocation guarantee is maintained.
- **Positive:** No dependency on any Result library.
- **Positive:** Idiomatic BCL pattern — no learning curve.
- **Negative:** Developers who prefer Railway-Oriented Programming must write a thin adapter.
  The adapter is trivial (3-5 lines) and is documented in the cookbook.
- **Documentation action:** Cookbook entry: "Integrating TryCreate with your Result<T> library."
  Documented in `docs/REJECTED-FEATURES.md`.
