# ADR-024: Reject Mutable Primitives

**Date:** 2026-08-10
**Status:** Accepted
**Authors:** Core maintainers
**Related audit items:** REJECT-003 (feature-gaps.md)

---

## Context

Some legacy DDD libraries and custom base classes support mutable Value Objects — objects that
expose setters or mutation methods. Examples include the old `ValueOf` library pattern and some
Entity Framework-first designs that require settable properties for change tracking.

`EricksonLopez.DomainPrimitives` generates `readonly partial record struct` types, which are
immutable at the language level.

---

## Decision

**`EricksonLopez.DomainPrimitives` will never generate mutable domain primitives.**

All generated types are permanently `readonly partial record struct`. No setter, mutation method,
or `with`-expression pattern will be generated that allows the value to change after construction.

---

## Rationale

### 1. Immutability is the definition of a Value Object

Eric Evans' original DDD definition of a Value Object states:
> "An object that represents a descriptive aspect of the domain with no conceptual identity.
> Value Objects are instantiated to represent elements of the design that we care about only
> for *what* they are, not *who* they are."

A Value Object's *what* is its value. If the value can change, the object ceases to be a Value
Object and becomes an Entity (with identity that persists through mutations). A mutable
"Value Object" is an oxymoron.

### 2. Mutable structs are a well-known C# anti-pattern

C# structs that expose mutation (either through setters or mutation methods) behave incorrectly
in many standard collection and LINQ scenarios:

```csharp
// Anti-pattern: mutable struct value in a dictionary
var dict = new Dictionary<MutableEmail, string>();
var email = new MutableEmail("a@b.com");
dict[email] = "value";
email.SetDomain("c.com"); // mutation changes hash code
bool found = dict.ContainsKey(email); // false — hash code no longer matches key
```

`readonly record struct` prevents this at the language level.

### 3. Entity Framework change tracking is a solvable problem without mutability

The typical argument for mutable Value Objects is EF Core change tracking — "EF needs to set
properties." This is addressed correctly by:

- Using the generated `ValueConverter<TModel, TProvider>` (already generated by DP).
- Configuring EF to use the ValueConverter for the primitive type.
- EF stores and retrieves the backing value through the converter — the domain primitive itself
  is never mutated; a new instance is created from the stored value on materialization.

This is the correct EF Core pattern and is already implemented in the
`EricksonLopez.DomainPrimitives.EFCore` package.

### 4. `with` expressions are acceptable but do not create mutability

C# `record struct` supports `with` expressions:

```csharp
var original = EmailAddress.Create("a@b.com");
var copy = original with { Value = "b@c.com" }; // creates a new instance
```

However, `with` on a `readonly record struct` creates a **new instance** — it does not mutate
the original. This is fine and is not a form of mutability.

---

## Alternatives Considered

| Alternative | Rejected because |
|-------------|-----------------|
| Opt-in `[StringPrimitive(Mutable = true)]` for EF scenarios | The EF scenario is solved correctly by ValueConverter without mutability. The opt-in flag signals that the library tolerates a design violation. |
| Generate a mutable DTO alongside the immutable primitive | Doubles the generated code, creates confusion about which type to use in which context, and adds maintenance burden. |
| Use `record class` (reference type) instead of `record struct` | Reference types are not immutable by default. `record class` with init-only setters is closer to correct, but this is the ADR-018 question (class support), which is also rejected. |

---

## Consequences

- **Positive:** All generated types have guaranteed thread safety.
- **Positive:** Hash codes remain stable for the lifetime of an instance.
- **Positive:** Can be safely used as dictionary keys and in LINQ groupings.
- **Negative:** Users from legacy mutable VO patterns need to refactor to use immutable
  primitives with EF ValueConverters.
- **Documentation action:** Documented in `docs/REJECTED-FEATURES.md`. Migration guide in
  `docs/migration/` explains the EF Core ValueConverter approach.
